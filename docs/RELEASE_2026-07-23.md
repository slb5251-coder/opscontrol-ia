## Plano de rollback do frontend

Em caso de falha crítica após a publicação:

1. restaurar a branch `main` para `bbcb9f59f0efa57fd41880cdb4cf07c08747de73`; ou
2. utilizar `backup-before-release-20260723` como origem da restauração;
3. confirmar o novo deploy do GitHub Pages;
4. limpar o cache do service worker ou atualizar a versão de cache para forçar a substituição dos arquivos.

## Plano de correção do banco

Não realizar downgrade destrutivo nem apagar dados de produção. Alterações de banco devem ser revertidas por uma nova migration de reparo.

Possíveis reparos:

- restaurar permissões específicas somente quando um fluxo autenticado comprovadamente depender delas;
- recriar uma política RLS anterior de forma explícita e limitada;
- substituir RPCs por uma versão corrigida usando `create or replace function`;
- remover índices novos somente após confirmar que não sustentam uma chave estrangeira ou consulta crítica;
- manter as colunas de observabilidade, pois são aditivas e não alteram os registros operacionais existentes.
